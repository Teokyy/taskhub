# TaskHub — аудит перед миграцией комнат

**Ветка:** `refactor/rooms-core`  
**Основание:** текущие файлы `taskhub_release/app/db.py`, `main.py`, `auth.py`, `bot.py`, `static/app.js`, конфигурация Railway в репозитории.  
**Статус:** аудит исходного кода; production-база не открывалась и не изменялась.

## 1. Текущее состояние схемы

Текущие таблицы:
- `users`
- `projects`
- `stages`
- `tours`
- `tasks`
- `submissions`
- `ledger`
- `audit`
- `task_criteria`
- `criterion_results`
- `disputes`
- `payouts`

В схеме отсутствуют:
- `rooms`
- `room_members`
- приглашения в комнаты;
- отдельное членство/рабочий режим пользователя по комнате;
- комнатные настройки выплат;
- неизменяемые снимки выплат с детализацией начислений.

У `projects`, `stages`, `tours`, `tasks`, `ledger`, `payouts` нет `room_id`. Поэтому текущая модель не обеспечивает изоляцию по комнатам.

## 2. Найденные расхождения с архитектурой v1.4

### Критические

1. **Глобальные права.** `users.role` содержит глобальное значение `admin/helper`. API использует его для управления проектами, модерации, просмотра задач и проверки работ. Это не соответствует ролям владельца/администратора/участника внутри комнаты.
2. **Нет изоляции API.** `/api/projects`, `/api/tasks`, `/api/team`, `/api/ledger`, `/api/review` и `/api/moderation` работают с глобальными данными и не проверяют членство в комнате.
3. **Резерв до публикации.** В `create_task` значение `budget_reserved_kop` сразу устанавливается равным вознаграждению, хотя задача создаётся в `pending`. По v1.4 резерв должен создаваться только при переходе в `available`.
4. **Модерация не атомарна с резервом.** Одобрение переводит задачу в `available`, но не выполняет отдельную проверку/создание резерва в момент публикации.
5. **Проверка работы не закреплена за автором.** `/api/review` доступен глобальному администратору, а `decide` не проверяет `created_by == current_user.id`. Проверка лишь запрещает исполнителю принимать собственную работу.
6. **Выплаты не имеют снимка.** `payouts` содержит сумму и период, но не комнату и не список включённых начислений. Уникальность `(user_id, period_start, period_end)` не моделирует комнатную выплату и не защищает состав снимка.
7. **Ledger не готов к компенсациям.** Ограничение `UNIQUE(task_id, kind)` допускает только одну запись данного вида на задачу и мешает нескольким корректирующим операциям одного типа.

### Существенные

8. **Режимов работы нет.** В базе нет режима заказчика/исполнителя ни глобально, ни по комнате. Текущий API запрещает глобальным администраторам брать задачи, связывая рабочее поведение с административной ролью.
9. **Жизненный цикл неполный.** Нет явного отказа исполнителя, отмены `pending`, срока доработки как отдельного поля и событий переходов с полной историей.
10. **Дедлайн.** Фоновый процесс использует `date(deadline) < date('now')`, то есть сравнивает даты, а не точное время. Для `revision` использует тот же исходный `deadline`. Нет напоминаний заказчику для `submitted`.
11. **Критерии и сдачи.** `submissions` хранит несколько отправок, но нет явной версии/номера и снимка критериев на момент публикации, кроме флага `criteria_frozen`.
12. **Баланс глобальный.** `/api/me` суммирует ledger пользователя по всей базе, а не в контексте выбранной комнаты.
13. **Аудит переходов неполный.** Таблица `audit` универсальная, но в ней нет обязательной структурированной модели события статуса, старого/нового статуса и идемпотентного ключа.

## 3. Риски миграции

- Существующие идентификаторы сущностей следует сохранить.
- Существующие пользователи, проекты, этапы, туры, задачи, сдачи, критерии, споры, ledger, audit и payouts должны остаться доступными после переноса.
- Все существующие сущности необходимо поместить в одну комнату по умолчанию, но нельзя создавать её до резервного копирования и проверки фактической базы.
- Нельзя выводить членство или роль из `users.role` без отдельного согласованного правила миграции.
- Нельзя считать текущие значения `budget_reserved_kop` корректными резервами: в текущем коде они выставляются ещё на этапе `pending`.
- Нужно отдельно сверить сумму ledger и суммы выплат до и после миграции.
- Старые выплаты нельзя искусственно превращать в подробные неизменяемые снимки, если исходных строк начислений недостаточно для восстановления их состава. Их следует сохранить как исторические выплаты с признаком legacy.

## 4. Резервное копирование

Production SQLite находится по пути, определяемому `app.db.DB_PATH`. По умолчанию при подключённом Railway Volume это обычно `/data/taskhub.sqlite3`, но переменная `DB_PATH` может переопределить путь.

Для создания согласованной копии добавлен скрипт:

```bash
cd taskhub_release
python scripts/backup_sqlite.py
```

Скрипт использует SQLite Online Backup API, не копирует файл базы напрямую и не изменяет исходную БД. Он сохраняет копию в `backups/` рядом с базой, проверяет `PRAGMA integrity_check` и `PRAGMA foreign_key_check`, устанавливает права файла `0600`.

**Важно:** скрипт необходимо запустить внутри Railway-сервиса, где смонтирован рабочий Volume. Из GitHub выполнить резервное копирование production-файла невозможно. Не продолжать миграцию, если резервная копия не создана и проверки не прошли.

## 5. Конфигурационные замечания

- Приложение и `railway.json` находятся в `taskhub_release/`, а корневой `README.md` не содержит конфигурации запуска. Фактический Railway Root Directory нужно проверить в панели проекта. Для текущей структуры приложение ожидает рабочую директорию `taskhub_release`.
- `taskhub_release/README.md` упоминает Root Directory `/` только условно; это не подтверждает фактическую настройку Railway.
- `init_db()` выполняет создание таблиц и аддитивные изменения при старте приложения. Перед новой миграцией нужен явный номер версии схемы и отдельная миграционная команда, чтобы не выполнять преобразование данных неявно при каждом запуске.

## 6. Следующий безопасный порядок работ

1. Запустить `scripts/backup_sqlite.py` в Railway и сохранить путь к резервной копии.
2. Получить `integrity_check = ok` и ноль нарушений внешних ключей. Если старые нарушения есть — сначала разобрать их.
3. Снять фактический снимок схемы production-БД: таблицы, колонки, индексы, внешние ключи, количества строк и контрольные суммы финансовых агрегатов.
4. Зафиксировать исходные контрольные значения: число пользователей/проектов/задач/сдач/ledger/payouts, сумму ledger по пользователям, суммы резервов по проектам и этапам.
5. Разработать миграцию на копии БД и проверить сохранение ID, строк и финансовых агрегатов.
6. Только после проверки подготовить перенос в production с возможностью отката на резервную копию.

**Не запускать миграцию на production и не менять рабочую базу на этом этапе.**
